Jev 是怎么工作的

Jev 是 TypeSafe 的 "System One" 模型：它不生成文本。你把当前状态（state）和几个类型化的问题一起发过去，它在你事先给定的选项上分配概率，返回类型化的答案。输出空间在请求里就已经定义死，所以不可能"编造"一个不存在的选项，也不需要解析自然语言。

① State（状态）

任意文本 / JSON：一条客服消息、一段新闻、传感器读数、一个棋盘……最多 32k tokens。
"I was charged twice for order A-104."
→

② Questions（类型化问题）

每个问题声明类型和允许的输出集合。
department: choice
  billing   "Charges, refunds"
  technical "Bugs, integrations"
  sales     "Pricing, plans"
→

③ Jev：只在槽位上打分

一次前向计算，并行给每个候选打概率（不逐 token 生成）：
billing
0.94
technical
0.04
sales
0.02
→ choice: "billing", confidence: 0.91

和通用 LLM 做同一件事的路径对比

通用 LLM（生成 → 解析）

写 prompt→逐 token 生成一段话→正则 / JSON 解析→校验枚举值→失败就重试→值
  • 秒级延迟，输出 token 计费
  • 可能返回不在集合里的答案、格式错误、多余解释
  • "置信度"要靠再问一遍或多次采样估计

Jev（打分 → 直接用）

state + questions→并行打分→类型化值 + 概率 + 置信度
  • 70–500 ms 端到端；输出免费，只按输入 $0.042 / M tokens 计
  • 结构上不可能出现类型错误或编造选项（训练方法 RLCD 专门优化概率校准）
  • confidence 是一等公民：代码用它决定"自动执行 / 请用户确认 / 转人工"

三个关键概念

校准概率（Calibrated）

当 Jev 说某个选项概率 0.8 时，在大量同类判断里它大约有 80% 是对的。概率是"可信的数字"，不是装饰。

置信度（Confidence）

由概率分布的形状算出的 0–1 单值：集中在一个选项 → 高；分散 → 低。它回答的是"该不该按这个答案行动"，而不是"答案是什么"。

扇出（Fan-out）

一次请求可带很多问题（包括"以防万一"的问题），state 只算一次 token。官方 cookbook 里 13 个问题合并成一次调用，比分开问便宜 12 倍、快 10 倍。

三种问题类型（Primitives）

所有决策都由这三种原语组合而成。每张卡片右侧是官方接口的真实响应结构，点"试一下"会把该示例装进 Playground 并立即发送。

如何选择

你要问的是…用例子
某个陈述是否成立noul"用户是否在要求退款？" "这段文字是否包含新信息？"
从一组互斥选项里挑一个（≤255 项）choice路由到哪个部门、意图分类、该调用哪个函数、五子棋下一步落在哪
在有序量表上定位（级别有描述）score情绪 0–4、严重程度 0–3、相关性 0–2；返回值可以是小数（如 1.9 = 介于 1 和 2 之间偏 2）

写法要点：instructions 里用反引号引用 state 的字段名（如 `description`）；选项/等级的描述越具体，概率越可信；state 目前英文最可靠。

    优势与局限
    
  
    Jev（System One）通用 LLM
    
    
    输出类型化值 + 每个选项的校准概率 + 置信度自由文本，需要解析、校验
    
    
    幻觉 / 类型错误结构上不可能——输出空间在请求里定义好需要重试、guardrail、schema 校验
    
    
    延迟70–500 ms（本页每次请求都显示实测值）秒级到分钟级
    
    
    价格$0.042 / M 输入 token，输出免费高 1–2 个数量级；输出 token 另计
    
    
    不确定性原生 confidence，可直接做阈值路由需要额外提示、多次采样或 logprobs
    
    
    批量一次请求多个问题，state 只计一次每个问题通常要一次生成
    
    
    速率250k tokens/s · 1200 请求/分（动态调整）视供应商
    
  
    
  
    什么时候不该用它
    
  
      
    
    • 需要生成文字、代码、解释的任务——Jev 不写任何东西。
      • 
    
    • 答案集合无法事先枚举（开放式抽取）。变通：先用规则/正则产出候选，再让 Jev 选（官方 "Pre-parsed Value Extraction" cookbook）。
      • 
    
    • 非英文输入、图片 / 音频输入——目前纯文本，英文最可靠。
      • 
    
    • 需要多步推理的复杂判断——官方建议拆成多个原子问题（Composite Scoring），由代码组合。
      • 
  
    
  
    本页用到的三个官方模式
    
  
    
    
    Composite Scoring
    新闻场景：4 个原子答案 → 代码里的公式 → 一个信号。权重可审计、可调。
    
    
    Confidence-Gated Routing
    控制场景：置信度 ≥ 阈值直接执行，否则要求确认；安全敏感动作阈值更高。
    
    
    Fan-out + 高基数 Choice
    五子棋场景：一次请求 4 个问题；"最佳落点"的候选集合就是所有空位。
